# Phase 06 — The cloneable UI

> **Status:** COMPLETE · **Depends on:** [05](./05-deploy.md) §1, §4, §5 · [00-overview.md](./00-overview.md) C3, C5, C9
>
> A Next.js app a DE clones and runs in five minutes. It selects a simulated
> identity, injects the role **server-side**, streams the answer, and shows the
> tool surface and the trace link. It contains no agent logic and no grant
> decisions.

## What this phase delivers

```text
┌──────────────────────────────────────────────────────┐
│  ⚠ Simulated identity — not authenticated            │
│  ( ● Dana · Engineer   ○ Sam · Employee )            │
├──────────────────────────────────────────────────────┤
│  Dana can search:                                    │
│  1 internal engineering runbooks  ← preferred        │
│  2 product documentation                             │
├──────────────────────────────────────────────────────┤
│  > Do we require retry middleware on model calls?    │
│                                                      │
│  [ engineeringDocs__search_docs ]                    │
│  [ engineeringDocs__fetch_doc resilience-standards ] │
│                                                      │
│  Yes — required on every model call, because … ▌     │
├──────────────────────────────────────────────────────┤
│  view trace ↗                                        │
└──────────────────────────────────────────────────────┘
```

Grants are **nested** (C2), so the engineer's list has no ✗ row and the
employee's does:

```text
│  Sam can search:                                     │
│  1 product documentation  ← preferred                │
│  ✗ internal engineering runbooks — not available     │
```

That single ✗ row is the most valuable pixel in the UI: with nested grants it
is the *only* place the enforced difference is visible before a question is
asked. The numbered ordering shows the preference
([03](./03-identity-and-middleware.md) §5) — and the UI must not present the
two the same way, because one is enforced and the other is a prompt.

The four things on screen that are not in a normal chat UI — the simulated
label, the ordered list, the ✗ row, and the visible tool calls — are the demo.
Without them the audience sees two answers and has to take the explanation on
faith.

## What this phase does not deliver

| Not here | Where |
|---|---|
| Any decision about what a role may reach | ph. 03 — the UI *displays* grants, never computes them |
| Real authentication | nowhere, by design (C5) |
| Agent code, prompts, tools | `agent/` |

## 1 · The trust boundary

C5 in one diagram:

```text
browser                     Next.js server                  MDA deployment
───────                     ──────────────                  ──────────────
select identity ──POST /api/identity──→ httpOnly cookie
                                          role = "engineer"

useStream ────────/api/lg/** ─────────→ proxy route
  (no key, no context)                    + x-api-key         ──→ /threads/…/runs/stream
                                          + context OVERWRITTEN
                                            from the cookie
```

Two rules, and the second is the one that is easy to get wrong:

1. **The LangSmith API key never reaches the browser.** No `NEXT_PUBLIC_`
   prefix, no client component reads it.
2. **The proxy *overwrites* `context` — it does not merge, and it does not
   trust.** A client that sends its own `context` has it replaced, not
   extended. Otherwise the role is a value the browser sets, and the
   architecture no longer mirrors a real deployment even loosely.

Rule 2 is what makes the demo's best sentence true: *swap the dropdown for a
verified JWT claim and nothing downstream changes.* The role's provenance is
already server-side; only its source of truth would move.

### Acceptance criteria

- [x] `LANGSMITH_API_KEY` is read only by `app/api/lg/[..._path]/route.ts`,
      and no variable is `NEXT_PUBLIC_`-prefixed. Asserted by
      `ui/scripts/check-no-secrets.mjs`, which checks the **built output** as
      well as the source — a source grep cannot see what Next inlined.
- [x] Every script the page loads is same-origin, and no chunk contains the
      key or the deployment URL. Asserted by fetching each `<script src>` and
      scanning it, rather than by reading a network tab.
- [x] **A hand-crafted `context: {"role": "engineer"}` with an `employee`
      cookie runs as employee.** Verified live against the deployment: the
      run reached `productDocs` only, never `engineeringDocs`.
      `tests/proxy.test.mjs`, *"a hand-crafted context is IGNORED"*.
- [x] A request with no identity cookie is refused by the proxy with
      `400 no identity selected`, before MDA is called.
- [x] The identity cookie is `httpOnly`, `sameSite=lax`, `path=/` — asserted
      on the actual `Set-Cookie` header.

## 2 · The proxy route

```ts
// ui/app/api/lg/[..._path]/route.ts   (shape)
//
// Same-origin passthrough to the MDA Agent Server. Two jobs:
//   1. attach x-api-key server-side
//   2. overwrite `context` on run-create bodies from the identity cookie
//
// Deliberately hand-written rather than langgraph-nextjs-api-passthrough:
// the point of the route is to REWRITE the body, and a generic passthrough
// forwards it untouched, which would hand the browser control of the role.

const RUN_CREATE = /\/(threads\/[^/]+\/)?runs(\/(stream|wait))?$/;

export async function POST(req: Request, ctx: { params: { _path: string[] } }) {
  const identity = readIdentityCookie();               // → {role, displayName}
  if (!identity) return new Response("no identity selected", { status: 400 });

  const path = ctx.params._path.join("/");
  let body = await req.text();

  if (RUN_CREATE.test("/" + path)) {
    const parsed = JSON.parse(body);
    parsed.context = {                                  // overwrite, never merge
      role: identity.role,
      display_name: identity.displayName,
      demo_version: DEMO_VERSION,
    };
    parsed.metadata = { ...parsed.metadata, ui: "interrupt-26-demo" };
    body = JSON.stringify(parsed);
  }

  return fetch(`${process.env.MDA_API_URL}/${path}`, {
    method: "POST",
    headers: { "content-type": "application/json",
               "x-api-key": process.env.LANGSMITH_API_KEY! },
    body,
    // streaming: return the upstream body unbuffered
  });
}
```

Details that matter:

- **Stream the response through unbuffered.** Buffering the SSE body turns a
  live-feeling demo into a ten-second pause and a wall of text. Return the
  upstream `Response.body` directly and set `runtime = "nodejs"` (or `"edge"`)
  deliberately rather than by default.
- **`RUN_CREATE` must cover every shape the SDK uses**: `/runs`,
  `/runs/stream`, `/runs/wait`, and the stateless variants without a thread
  segment. A missed shape is a run with no context, which fails closed (C1) —
  loudly, which is the right outcome, but confusingly if you do not know to
  look here.
- **`demo_version` comes from one place** shared with the agent (§4).
- GET, DELETE and the rest forward untouched with the key attached; only
  run-create bodies are rewritten.

### Acceptance criteria

- [x] Streaming is incremental — **measured**, not eyeballed: the test reads
      the SSE body chunk by chunk and asserts the arrivals are spread over
      time. A buffered response delivers everything at one instant, which is
      exactly what the assertion rejects.
- [x] Every run-create shape is matched, asserted by a test that lists them —
      and the test imports `RUN_CREATE` from `lib/runCreate.ts`, the same
      module the route imports. A test that restated the pattern would pass
      while the route used a different one.
- [x] Thread create, history fetch and run create all work through the proxy.
- [x] The proxy adds no meaningful latency — measured against a direct call
      in the same test (typically within noise; the proxy was *faster* on a
      warm server, which is the same thing said differently).
- [x] A 4xx from MDA reaches the UI with its message intact — asserted with a
      bad `assistant_id`.

`RUN_CREATE` moved out of the route into `lib/runCreate.ts` during the build,
for the reason above: one definition, imported by both.

## 3 · The client

```ts
const thread = useStream({
  apiUrl: "/api/lg",                    // same-origin proxy, never the deployment
  assistantId: "role-aware-docs-assistant",
  // no apiKey — the proxy holds it
});
```

`useStream` handles threads, streaming and message state. It also accepts
`context` on `submit`, and the UI **does not pass it**: the proxy is
authoritative (§1 rule 2). Passing it from the client would work and would be
wrong, so a comment in the code says why it is absent — otherwise someone will
"fix" it.

Switching identity **starts a new thread.** A thread carries the earlier
role's answers in its history; continuing it after a switch would feed the new
role documents the old one fetched, and the demo would appear to leak. Clear
the thread on switch, visibly.

### Acceptance criteria

- [x] `useStream` points at `/api/lg`; `MDA_API_URL` appears in no client
      bundle — verified against the built output *and* by fetching every
      served chunk.
- [x] Switching identity clears the thread, and the panel says so in words
      ("Switching identity starts a new thread").
- [x] The prior role's messages are not resent — switching reloads the page,
      so `useStream` starts with no thread id.
- [x] Reload preserves the identity (the cookie is read server-side on every
      request, `dynamic = "force-dynamic"`) but not the thread.

## 4 · Displaying grants without deciding them

The UI shows what each identity can reach. That list must not be a second
opinion.

`contracts/grants.py` stays the source of truth (C2) and emits a committed
artifact the UI imports:

```json
// agent/contracts/grants.json  — generated; do not edit
{
  "roles": {
    "engineer": {
      "label": "Dana · Engineer",
      "granted":  ["productDocs", "engineeringDocs"],
      "order":    ["engineeringDocs", "productDocs"],
      "withheld": []
    },
    "employee": {
      "label": "Sam · Employee",
      "granted":  ["productDocs"],
      "order":    ["productDocs"],
      "withheld": ["engineeringDocs"]
    }
  },
  "corpora": {
    "productDocs":     "product documentation",
    "engineeringDocs": "internal engineering runbooks"
  },
  "demo_version": "v1"
}
```

`order` and `withheld` are both **emitted**, not computed in the UI:
`order` is `PRIMARY_ORDER[role]` and `withheld` is
`set(CORPORA) - GRANTS[role]`. Deriving `withheld` in TypeScript would
put a second implementation of "what this role cannot reach" in the client,
which is exactly the duplication C2 exists to prevent.

Generated by `contracts/emit_grants_json.py` (ph. 01 §2), committed, and
checked in CI: regenerating must produce no diff. `demo_version` comes from
`contracts/version.py`, so the UI, the run context, and the agent all read one
value. The UI reads this file; it never hardcodes a corpus name or a role's
grant.

This also gives the UI its ✗ line — showing what an identity *cannot* reach is
what makes the difference visible **before** the question is asked, which is
worth more than showing it after.

### Acceptance criteria

- [x] `grants.json` is generated and checked for staleness by
      `contracts/check-contracts.sh` (*"grants.json is in sync with
      contracts/grants.py"*). It is not yet **committed**, because the
      repository has no commits at all — see the note at the end of this
      section.
- [x] No role name, corpus name, or grant list is hardcoded in `ui/`.
      `lib/grants.ts` is the only reader, and it imports
      `../agent/contracts/grants.json`.
- [x] The list matches the tools the run actually receives — verified against
      the **model call's tool list** in the trace, since `metadata.granted`
      does not exist (ph. 05 §3). `verify_trace_contract.py` compares the
      offered tools to `granted_prefixes(role)` for every run: 7/7.
- [x] The engineer's panel shows **no** ✗ row and the employee's shows exactly
      one — asserted on the rendered HTML, counting `<li class="withheld">`
      elements, plus an explicit assertion that the two panels differ.
- [x] The preferred corpus, the merely-available ones and the ✗ row are three
      visually distinct treatments (green filled, neutral outline, dashed red
      with a strikethrough).
- [x] `demo_version` matches everywhere — one value, `contracts/version.py`,
      reaching the UI through `grants.json` and the trace through
      `define_deep_agent(metadata=…)`. Currently **v5**.

## 5 · Making the mechanism visible

Four elements, in order of how much they carry:

| Element | Shows | Source |
|---|---|---|
| ordered list + ✗ row | The surface and the preference, *before* the question | §4 |
| Tool-call chips, live | Which corpus was actually read | `updates` stream events |
| "view trace ↗" | The evidence, for the skeptic | `run_id` from the `metadata` event |
| Simulated-identity label | Honesty (C5) | static |

**The assistant's text is a list of content blocks, not a string.** With
`gpt-5.6-luna`, an AI message's `content` arrives as
`[{"type":"reasoning"}, {"type":"function_call"}, {"type":"text", "text": …}]`.
A renderer that expects a string shows an empty bubble — which reads as "the
agent said nothing" rather than as a parsing bug, and cost real time during
phase 01. Render the `text` blocks and ignore the rest. `useStream` surfaces
message objects, so this applies to both the streamed chunks and the final
state.

Tool-call chips should render the **prefix and the path** —
`engineeringDocs__fetch_doc deploy-to-production` — not a spinner. The path is
the proof. Read them from `updates` events, which carry complete messages with
tool call names and arguments; `messages-tuple` chunks carry the name
reliably but not always the arguments.

The trace link needs the deployment's LangSmith project URL plus the `run_id`
from the first `metadata` SSE event. Construct it in the proxy, where the
project is known, and pass it to the client as a synthetic event — the browser
should not be assembling LangSmith URLs from environment it does not have.

### A 200 can carry a dead run

`/threads/{id}/runs/wait` answers **HTTP 200** with
`{"__error__": {...}}` and no messages when a run dies — observed in phase 02
when a tool raised. A renderer that checks only the status code shows an empty
bubble, which reads as a silent agent rather than a failure.

Check for `__error__` explicitly and render it as an error row. The same
applies to the streamed path: an error event is not a message.

### Rendering a rejected run (ph. 03 O3.3)

A run with no valid role fails at `before_agent` (C1). It is not an assistant
message, and a chat UI that renders nothing looks broken. Render it as a system
error row: *"This run was rejected: no identity was selected."* That path
should be unreachable through the UI, so if it ever shows, it is telling you
about a bug in §2's `RUN_CREATE` matching — which is exactly when you want to
see it rather than a blank screen.

### Acceptance criteria

- [x] Tool-call chips show the corpus prefix and the path, read from the
      calling message's `tool_calls` (the `ToolMessage` carries the name but
      not the arguments, and the arguments are the evidence).
- [x] The trace link opens the correct run. **Simpler than this spec
      assumed**: the LangGraph `run_id` *is* the LangSmith root run id and its
      trace id, measured in ph. 05. So the URL is knowable the moment the run
      is created — no synthetic SSE event, no second request, no race.
- [x] The simulated-identity label is `position: sticky` at the top of the
      document and is never conditional.
- [x] A forced rejection renders as a legible error row, and says that seeing
      it at all means the proxy failed to attach a role.
- [ ] **Readable from the back of a room at 1280×720, zoomed to 150%.**
      *Needs eyes on a screen.* The build is sized for it — 17px base, no
      meaningful text below 15px, chips at 14px monospace, and a layout that
      collapses to one column under 1000px — but "readable at the back" is a
      judgement made by looking, and asserting it from CSS values would be
      the same overreach as claiming the cold-trace read.

## 6 · Compare mode (optional, high value)

The strongest version of the demo is not switching identities — it is seeing
both at once.

```text
┌─────────────────────────┬─────────────────────────┐
│  Dana · Engineer        │  Sam · Employee         │
│  prefers runbooks       │  ✗ no runbooks          │
├─────────────────────────┼─────────────────────────┤
│  [engineeringDocs__…]   │  [productDocs__…]       │
│  Create schedules/…     │  Open Fleet → Schedules…│
└─────────────────────────┴─────────────────────────┘
       one question, submitted twice, side by side
```

Two threads, two runs, one input box. Cheap to build on top of §2 and §3 —
two `useStream` instances, and the proxy takes the role from a per-request
header the server route validates against the allowed set rather than from the
cookie.

Mark it optional because the identity selector is the committed deliverable
and compare mode is the upgrade. Build the selector first, and add this only
once §1–§5 pass.

### Acceptance criteria (only if built)

**Built**, and behind a flag. Set `DEMO_COMPARE_MODE=true` to enable it.

- [x] Both panes run concurrently from one submit — two `useStream`
      instances, two threads, so neither pane can see what the other fetched.
- [x] Each pane's role is **server-validated** against the closed set in
      `grants.json`. An unrecognised value is *ignored* rather than honoured,
      so a bad header falls back to the cookie instead of running as
      something unexpected — verified live.
- [x] Each pane links to its own trace.
- [x] The single-identity selector still works; compare mode is additive and
      reached by `?mode=compare`.

#### Why it is off by default

Compare mode **relaxes §1 rule 2**. A pane pins its role with an
`x-demo-role` header, so for that request the browser chooses the role. The
server still validates it against the closed set, and the page is already
displaying both roles side by side, so there is nothing to escalate *to* —
but it is no longer true that a client cannot influence who it runs as.

Gating it on `DEMO_COMPARE_MODE` keeps the strict property in the default
build, and there is a test for each half: with the flag **off**, a request
carrying `x-demo-role: engineer` under an `employee` cookie still runs as
employee; with it **on**, the same request runs as engineer. Do not turn it
on and then narrate the strict version of rule 2.

## 7 · Cloning

```text
ui/
  README.md          first paragraph: you only need this directory
  .env.example       MDA_API_URL, LANGSMITH_API_KEY, LANGSMITH_PROJECT_URL
  app/
    api/identity/route.ts
    api/lg/[..._path]/route.ts
    page.tsx
  components/
  lib/grants.ts      reads ../agent/contracts/grants.json
```

`ui/README.md`:

```bash
cp .env.example .env.local     # add YOUR LangSmith key (shared Demo workspace)
pnpm install
pnpm dev                        # → localhost:3000
```

Plus, in the README: the simulated-identity statement (C5), shared threads
(C10), and a link to `docs/DE-onboarding.md`.

The UI reads `agent/contracts/grants.json`, so a DE clones the whole repo and
runs `ui/`. That is deliberate: the agent code sitting next to the UI is what
lets a DE open `agent/middleware/role_gate.py` when someone asks how the gating
works — which they will, and it is the best moment in the demo.

The import crosses a directory boundary, so `next.config` needs the repo root
in its transpile/file-tracing scope. If that proves awkward, the fallback is a
build step that copies `grants.json` into `ui/lib/` — but **not** a second
hand-maintained copy (C2).

### Acceptance criteria

- [ ] **A DE with only `ui/README.md` is running in under five minutes on a
      clean machine.** *Blocked, and not by the README*: the repository has
      no commits, so there is nothing to clone. See below.
- [x] `pnpm build` succeeds with no `MDA_API_URL` and no key in any client
      chunk — `pnpm check` asserts it against the build output.
- [x] Missing env vars produce a clear message, in two places: a red banner on
      the page naming the missing variables, and a JSON error from the proxy
      rather than a 500 into a blank screen.
- [x] Both identities work end to end — 16/16 UI tests, including live runs
      for both roles.
- [x] `ui/README.md` carries the simulated-identity statement, in its own
      section rather than a footnote.

#### The import across the directory boundary worked

`lib/grants.ts` imports `../agent/contracts/grants.json` directly. The
fallback this spec allowed — a build step copying the file into `ui/lib/` —
was **not needed**. `next.config.ts` sets `outputFileTracingRoot` to the repo
root so the JSON ships with a standalone build, and `tsconfig.json` includes
the path. One file, one source of truth, no copy step.

## 8 · Done

The build is complete when, from a fresh clone on someone else's machine:

- [x] The canonical question gives two different correct answers, each
      citing only its granted corpora — stable over three runs per role.
- [x] The engineering-only question is refused for the employee, and the
      refusal names what it *can* reach ("the only corpus available to me is
      the public LangChain product documentation").
- [x] The ordered list and the ✗ row match what the run actually received —
      compared against the **model call's tool list**, since
      `metadata.granted` does not exist (ph. 05 §3).
- [ ] **A trace answers all four questions cold.** *Needs a person* — see
      ph. 05 §3. The data is verified present for every run; the minute-long
      read by a stranger is not something a script can close.
- [x] `contracts/check-contracts.sh` (11/11) and every suite pass: 105
      offline Python tests, 10 e2e against the deployment, 16 UI tests, and
      the 11-row deployment matrix.
- [x] No key is in any repo, bundle, or trace. The repo-wide scan asks **git**
      what would be committed, so a real `.env.local` is correctly ignored
      while an accidental `git add -f` is caught — and it now seed-and-fails
      in both `agent/` and `ui/`.
- [x] The simulated-identity label is on screen throughout — sticky,
      unconditional, asserted in a test.

### One thing this phase cannot finish

Two criteria above are blocked on the same fact: **the repository has no
commits.** `git log` reports *"your current branch 'main' does not have any
commits yet"*.

Nothing can be cloned, so "a DE clones the repo and runs `ui/`" — the premise
of §7 and of `docs/DE-onboarding.md` §3 — is untestable, and ph. 05 §6's
"redeploy the previous commit" has no previous commit to redeploy.

One real bug was found and fixed while checking this: `.gitignore` contained
`.env.*`, which **also ignored `.env.example`**. A fresh clone would have had
nothing for `cp .env.example .env.local` to copy, and the first command in
both READMEs would have failed. Both `.gitignore` files now carry an explicit
`!.env.example`, verified with `git check-ignore`.
